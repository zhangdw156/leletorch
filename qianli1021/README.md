## 第一段：超市促销——确定的方向错误

### 题意

货架上有 n 个商品，原编号从左到右为 1 到 n，价格为 a[i]。两人轮流拿商品：

1. 小丽先拿，选择当前价格最低的商品；同价取最左边。
2. 闺蜜后拿，选择当前价格最高的商品；同价取最右边。
3. 每次除选中的商品外，还拿走其当前左侧最多 k 个、右侧最多 k 个商品；不足 k 个就拿完该侧剩余商品。
4. 重复直至所有商品拿完，分别输出两人取得的原编号。保存的程序沿用原提交的输出约定：各一行，编号升序；没有商品时输出空行。

“当前左右相邻”指尚未被拿走的商品，所以数组模拟双向链表是合适的做法。

### 错在这一行

原代码：

```python
for j, direction in [(l, R), (r, R)]:
```

应当改为：

```python
for j, direction in [(l, L), (r, R)]:
```

`L[i]` 是当前左邻居，`R[i]` 是当前右邻居。左侧从 l 开始必须继续沿 L 走。原代码从左邻居出发却沿 R 走，删除中心商品后就会穿到右侧，与右侧循环重复取商品。

### 可以直接复现的反例

输入：

```text
5 2
5 4 1 3 2
```

最低价为编号 3，正确操作应拿走中心 3、左侧 2 和 1、右侧 4 和 5。因此第一行应为 `1 2 3 4 5`，第二行为空。

原代码的实际过程：

1. 删除编号 3，链表变成 `1 → 2 → 4 → 5`。
2. 左侧循环从编号 2 开始沿 R 走，删除 **2、4**。
3. 右侧循环仍从此前保存的编号 4 开始，删除 **4、5**。
4. 编号 4 被重复加入，编号 1 没有被拿走；但 cnt 已减到 0，循环提前结束。

首次整理时，本地运行原代码得到第一行 `2 3 4 4 5`；修正版得到 `1 2 3 4 5`。

另一个反例：

```text
3 2
2 1 3
```

原代码重复删除后会把 cnt 减成负数。`while cnt` 对负数仍然成立，最终从空堆取元素，实际报 `IndexError: index out of range`。

给 `remove()` 增加“已经删除则跳过”，或者把循环改成 `while cnt > 0`，都不能解决漏拿左侧商品的问题；必须修正方向。

### 为什么还能通过部分测试

当 k = 1 时，每侧只拿一个商品，保存的下一跳不会在该侧继续使用，所以写错方向不影响这一轮。若 k = 0，则不取两侧。中心在最左侧等情况也可能暂时避开错误。

这解释了错误具有条件性，但不能据此断言官方恰好有 82% 的测试属于这些情况。

双堆的同价规则写得正确：`(a[i], i)` 优先最低价、最小编号；`(-a[i], -i)` 优先最高价、最大编号。惰性删除也正确。

修正后每个商品只从链表删除一次，每个堆中的条目最多弹出一次，总时间 O(n log n)、空间 O(n)。两侧虽然写着 k 次循环，总成功删除次数仍然只有 n，不是 O(nk)。保存的修正版另用 owner 数组记录归属，再按编号扫描输出，省去了结果排序。

## 第二段：拥塞——算法成立，但 Python 重复搜索开销大

### 题意与已知限制

n × n 的路由器网格，包从左上角 (1,1) 发往右下角 (n,n)，每次可转发到上、下、左、右的相邻格子。中间路由器支持的最大包大小是 a[i][j]，包超过该容量就被丢弃。起点和终点为 -1，表示无限制。

最多转发 T 次，求可以送达的最大包大小。截图明确给出：

- `2 ≤ n ≤ 1000`，`1 ≤ T ≤ n²`。
- 除起终点外，容量在 `0..1_000_000`。
- C/C++ 时限 1000 ms、内存 65536 KB；其他语言时限 3000 ms、内存 589824 KB。

保存代码沿用原提交的约定：无法发送正大小的包时输出 0。截图未展示完整输出说明。

### 二分 + BFS 为什么正确

给定包大小 x，只保留容量至少为 x 的格子。用 BFS 判断起终点之间的最短路径是否不超过 T 步。

若 x 可以送达，更小的包也能沿同一路径送达；若 x 不能送达，更大的包也不行。可行性具有单调性，因此可以二分答案。

原代码中以下写法并非导致失败的逻辑错误：

- `T < 2 * (n - 1)` 时直接输出 0：这就是起终点的最小曼哈顿距离。
- 把 -1 替换为 `1_000_001`：普通格子最大容量只有 `1_000_000`，足够表示无限制。
- `while q and step <= T`：第 0 层是起点，允许到第 T 层检测终点，步数含义正确。只是第 T 层仍会入队第 T+1 层，做了无用扩展。
- `if not vis[np]` 内使用 `vis[np] += 1`：进入分支时值为 0，因此效果与赋值 1 相同；改成赋值更清楚，但不是主要瓶颈。
- 从 1 开始二分、初始答案为 0：没有正数可行时会保留 0。

### 超时来自什么

一次 BFS 最坏访问 n² 个格子，二分 `1..1_000_000` 最多约 20 次：

```text
时间：O(n² log A)，A = 1_000_000
空间：O(n²)

n = 1000 时：约 2000 万次格子出队，约 8000 万次方向检查。
```

原版还在每次出队时执行 `divmod(p, n)`、四方向边界判断、若干全局变量读取、容量及访问标记判断。Python 完成这些操作的代价明显大于同数量的简单机器指令。

小数据与大数据的耗时差距接近平方增长，因此小数据通过、大数据超时符合这个实现的表现。没有官方测试日志，不能证明 36% 对应某一个具体规模分界。

### 保存的优化做了什么

`拥塞.py` 仍然使用二分 + BFS，渐进复杂度不变，主要减少反复执行的操作：

1. 网格四周补一圈容量 -1；四邻居用下标 `p ± 1`、`p ± width` 访问，去掉 `divmod` 和四次边界判断。
2. 使用局部变量访问网格、访问标记与队列方法。
3. 用搜索轮次标记 visited，复用一个 bytearray。bytearray 每个元素占 1 字节，可保存 0～255 的整数；最多 20 轮，值不会超过其范围。该优化只减少少量初始化开销，主要收益仍来自循环内部。
4. 发现终点时立即成功；只从距离 0 到 T-1 的层向外扩展，因此接受的路径最多 T 步。
5. 使用缓冲输入，按行读取，避免同时保留百万个输入字符串。

**当前 Python 优化版没有提交到原评测平台，不能标记为已 AC。**

### 不可直接替换的思路

不能直接换成不限制步数的“最大瓶颈路径 Dijkstra”或按容量合并的并查集：它们只能判断容量或连通性，可能找到一条超过 T 步的路。

也不能一般地只向右、向下做动态规划：容量高的可行路径可能必须向上、向左绕行。只有当允许的路径长度不足以容纳绕行，例如 T 恰好等于最小距离时，才可以利用这个特殊条件。

首次整理时的验证包含如下自造网格：

```text
-1 0 9 9 9
 9 0 9 0 9
 9 0 9 0 9
 9 0 9 0 9
 9 9 9 0 -1
```

包大小 9 的通道必须先向下、再向右、向上、向右、向下，最短 16 步。T = 15 时答案为 0，T = 16 时答案为 9。首次整理时已验证，原代码与 Python 优化版均正确区分这两种情况。
